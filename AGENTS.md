# Работа над игрой

Правила адаптированы из Project Wisp под локальную браузерную игру.

- Делать один небольшой законченный этап за итерацию. Не реализовывать весь план альфы за один заход. Каждый этап завершать отдельным тематическим коммитом.
- Альфа: приоритеты — хорошая архитектура, скорость разработки и экономия токенов. Не вводить постоянные тестовые циклы, обязательные сборки и документацию на каждую мелочь.
- Архитектуру определяет отдельный субагент-архитектор по `docs/ARCHITECT.md`. Перед реализацией новой игровой системы или изменением границ модулей основной агент запускает архитектора и следует его решению. Для мелких исправлений в существующей архитектуре повторный вызов не нужен.
- До изменений определить scope и критерии готовности. План продукта и статус этапов — `docs/ALPHA_PLAN.md`.
- Сохранять чужие изменения. Не делать push, переписывание истории и замену стека без отдельного поручения.
- Игровые правила в `src/game/core` не зависят от React, Phaser, DOM или хранилища браузера. Создание адаптеров — в session/presentation, зависимости передаются явно.
- Presentation отображает состояние и передаёт команды; урон, награды, инвентарь и прогрессия принадлежат игровой логике.
- Разделять состояние уровня, состояние забега и постоянный профиль. Загрузка следующего уровня не должна создавать новый забег. Сохранение профиля выполняется через проверяемый адаптер.
- TypeScript strict; избегать `any`, подавления ошибок и двойных приведений типов. Явные контракты до реализации, ориентир до 300 строк на модуль.
- Использовать существующие зависимости и абстракции. Новые зависимости вводить только с объяснением необходимости; не строить инфраструктуру под гипотетические задачи.
- Исправлять конкретные ошибки и сохранять архитектурные границы; не расширять рефакторинг без необходимости. Новые тесты не являются обязательным условием багфикса.
- Проверки выбирать по необходимости: просмотр diff, проверка типов, ручной запуск или точечный тест — минимально достаточный вариант для изменения. `npm test` и `npm run build` не обязательны перед каждым коммитом; запускать при конкретной причине или по просьбе пользователя. Существующие тесты сохранять, но не дополнять и не запускать автоматически ради процесса.
- Ассеты использовать из проекта; отсутствие нужной графики указывать явно. Не выдавать placeholder за готовый арт.
- Архитектор определяет структуру и контракты, основной агент реализует. Отдельное повторное ревью не обязательно. Устранять подтверждённые проблемы в пределах текущего этапа; остальные кратко записывать в план.
- В отчёте: что изменено, какие проверки выполнены, коммит и следующий этап. Не называть игру альфой до выполнения критериев ниже.
